# Oh My Canvas 기여 가이드

[English](../../CONTRIBUTING.md) · **한국어** · [日本語](ja.md) · [简体中文](zh-CN.md)

재현 가능한 버그 제보, 번역 개선, 컴포넌트 수정, 범위가 명확한 코드 변경으로 함께 개선할 수 있습니다.

> **라이선스와 출처를 확인하세요.** 프로젝트의 독립 작성 코드에는 [MIT 라이선스](../../LICENSE)가 적용되며, 외부 자료는 각자의 이용 조건을 유지합니다. 기여할 권리가 있는 자료만 제출하고 [외부 고지](../../THIRD_PARTY_NOTICES.md)를 보존하세요. 제거한 회사 코드나 복사한 테스트를 다시 포함하지 마세요. 별도의 CLA·권리 양도를 새로 요구하지 않습니다.

## 기여할 내용 고르기

| 종류 | 함께 제출할 내용 |
| --- | --- |
| 버그 수정 | 최소 합성 예제, 기대·실제 결과, 회귀 검사 |
| UI 개선 | 실제 변경 전후 화면, 키보드·포커스 동작, 관련 창 크기 확인 |
| 컴포넌트·variant | 원본과 인스턴스, override, Undo, 저장·재열기 검사 |

| 큰 기능 | 구현 전에 구체적 문제, 사용 사례, 범위, 대안과 비용 |

현재는 로컬에서 관리하며 공개 원격 저장소가 설정되어 있지 않습니다. 이슈·PR 템플릿은 나중에 호스팅할 때 사용할 준비 문서입니다. 그전에는 같은 양식으로 로컬 보고서·검토 메모를 작성하세요. 공개 이슈 트래커·릴리스·자동 CI가 있다고 가정하지 마세요.

## 로컬 개발

허가받은 체크아웃과 Node.js **22.12 이상**, npm을 준비하고 저장소 루트에서 실행합니다.

```sh
npm ci
npm run build
npm start
```

개발 중에는 `npm run dev`를 사용할 수 있습니다. 새 로컬 수용 검사는 macOS arm64에서 실행하며, 통과한 검사와 남은 작업은 [현재 검증 기록](../independent/VERIFICATION.md)에 구분합니다. Windows/Linux 실행은 미검증입니다. 패키지 앱의 MCP CLI에는 별도 Node 설치가 필요 없습니다.

실제 중요 문서 대신 합성 문서와 별도 테스트 프로필을 사용하세요. 저장·형식 변경을 시험하기 전에는 `.omc` 백업을 내보내세요. [시작 안내](../GETTING_STARTED.md)와 [구조 안내](../ARCHITECTURE.md)도 참고할 수 있습니다.

## 변경과 검토 순서

1. 합의한 기준 커밋에서 `fix/text-undo`, `feat/component-property`, `docs/korean-readme`처럼 목적이 보이는 브랜치를 만듭니다. 다른 작업은 보존합니다.
2. 먼저 문제를 재현하고 호출 경로를 확인합니다. 기존 편집기·저장·UI 패턴을 재사용합니다.
3. 한 번에 검토할 수 있는 범위로 변경하고, 중요한 동작에는 회귀 검사를 추가합니다. 동작·호환성이 바뀌면 문서도 수정합니다.
4. 영향받는 검사를 실행하고 실행하지 못한 검사는 그대로 적습니다.
5. 개인정보·비밀·생성 파일·무관한 변경이 없는지 diff를 확인합니다. 커밋 제목은 `fix: preserve text session undo`처럼 명확한 영어로 작성합니다.
6. [PR 템플릿](../../.github/PULL_REQUEST_TEMPLATE.md)으로 PR 또는 로컬 검토 메모를 작성합니다. 관리자 승인 없이 병합·공개·배포하지 않습니다.

## 필요한 검사 선택

일반 개발 검사는 로컬에서 실행하며 Docker 준비가 필요하지 않습니다.

```sh
npm run check
npm test
npm run test:editor
```

앱 통합 변경은 먼저 빌드한 뒤 관련 실제 Electron 검사를 고릅니다.

```sh
npm run build
npm run test:e2e
node scripts/independent-host-e2e.mjs
node scripts/independent-ui-e2e.mjs
node scripts/independent-render-e2e.mjs
node scripts/independent-library-e2e.mjs
```

각 스크립트는 별도의 수용 검사입니다. 변경과 관련된 것을 선택하고 실제 명령·결과를 기록하세요. 임시 프로필로 실제 앱을 띄우며, 일부는 `docs/qa/`의 화면·결과를 갱신합니다. 생성 결과를 무조건 커밋하지 말고 확인하세요. 샌드박스에서는 loopback/TLS와 Electron 시작에 호스트의 정상 실행 권한이 필요할 수 있습니다.

패키징 변경은 먼저 빌드한 뒤 로컬 스테이징 도구를 사용합니다. 이 도구는 잠긴 런타임 의존성을 작업 전용 폴더에 실제 파일로 복사하고 설치된 Electron을 재사용합니다. 다른 worktree를 가리키는 `node_modules` 링크로 직접 패키징하면 의존성이 빠질 수 있습니다.

```sh
npm run build
node scripts/package-local.mjs
node scripts/packaged-smoke.mjs
```

이 명령은 로컬 산출물만 만들고 검사하며 공개하거나 설치본을 교체하지 않습니다. 관련 없는 검사를 위해 설치 앱이나 전역 MCP 설정을 바꾸지 마세요. 이전 `--installed`·기본 프로필 스크립트는 현재 독립 엔진의 수용 검사 경로가 아닙니다. 별도로 허가받고 검토한 설치 확인에서만 사용하세요.

문서만 바꿀 때는 `node scripts/check-docs.mjs`를 실행하고 렌더링된 이미지와 번역을 검토하세요. 보통 앱 전체를 다시 빌드할 필요는 없습니다. [검사 안내](../TESTING.md), [문제 해결](../TROUBLESHOOTING.md), [최신 검증 기록](../independent/VERIFICATION.md)을 참고하세요. 과거 테스트 개수는 해당 시점의 기록입니다.

## 지켜야 할 동작

- 저장은 원자적 쓰기·백업 복구·실제 상태 변경 전 검증과 용량 제한을 유지합니다.
- 협업은 수렴·참여자별 Undo·좌표 일관성·인원 제한을 유지합니다. 같은 컴퓨터의 4인 TLS 검사가 외부 인터넷/NAT 도달성을 입증하지는 않습니다.
- MCP는 인증·Origin/Host 검사와 loopback 바인딩을 유지합니다. **MCP 포트를 포워딩하지 마세요.** 사용자 텍스트 편집·값 스크럽 중 읽기는 허용하고 변경은 작업 종료까지 `busy`를 반환합니다.
- 저장·협업은 v2를 쓰고 v1 문서는 계속 읽습니다. 호환성을 검사하고 다른 프로토콜을 조용히 섞지 마세요.
- 원격 에셋·텔레메트리·계정·유료 서비스 의존성을 명시적 제품 결정 없이 추가하지 마세요.

## 버그와 기능 제안

[버그 양식](../../.github/ISSUE_TEMPLATE/bug_report.yml)에 앱·소스 커밋, OS·아키텍처, 정확한 재현 단계, 기대·실제 결과를 적습니다. 관련 있다면 저장·재열기, Undo, 호스트·참여자 수와 연결 상태도 기록합니다.

첨부물은 최소 합성 문서와 비식별 화면·로그만 사용하세요. 실제 고객 디자인, 개인 기록, 자격 증명, 세션 초대, 토큰, `mcp-runtime.json`, 사용자 데이터 폴더 전체는 첨부하지 마세요. 초대는 편집 권한을 주며 `.omc`에는 이미지와 병합 이력이 들어 있습니다. 화면의 레이어를 삭제했다고 과거 내용까지 제거되는 것은 아닙니다. 새 합성 문서에서 재현하세요.

보안 문제는 [보안 안내](../../SECURITY.md)를 따르세요. 민감한 내용·실사용 비밀·타인 시스템을 대상으로 한 공격 코드를 공개 이슈에 올리지 말고, 관리자와 이미 합의한 비공개 채널을 사용하세요. 지정된 별도 신고 이메일이나 응답 기한을 가정하지 마세요.

[기능 양식](../../.github/ISSUE_TEMPLATE/feature_request.yml)에는 문제와 가장 작은 해결 동작, 대안, 저장·협업·MCP·권한·네트워크 영향을 적습니다. 검토 전에 구현이나 출시일을 약속하지 마세요.

## 번역과 리뷰

명령·공통 기술 사실은 영문 README와 [영문 기여 가이드](../../CONTRIBUTING.md)를 기준으로 맞춥니다. 사전 조건, 수치, 형식, 한계, 검증 플랫폼이 바뀌면 관련 네 언어를 함께 확인하세요. 실제 영어 UI 라벨·도구명·API·명령은 그대로 두고 설명을 번역합니다.

오프라인 체크아웃에서도 열리도록 상대 링크와 저장소 이미지를 쓰고 대체 텍스트를 넣습니다. 실제 앱 화면을 사용하고, 없는 기능이나 개인 문서를 보여주지 마세요. 리뷰에서는 사람보다 동작·근거·코드를 구체적으로 논의합니다.
